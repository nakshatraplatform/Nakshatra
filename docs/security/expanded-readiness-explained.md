# VivIntro readiness fixes in plain language

These fixes are implemented on `security/nak-74-expanded-readiness-fixes`. Local verification is recorded in the engineering feature record. Production deployment, migration application, scheduler activation and confirmation that the live retention backlog is cleared remain separate steps. Email authentication and DMARC were excluded at the owner's request.

| Finding | What was wrong | How we fixed it | A useful interview lesson |
| --- | --- | --- | --- |
| DEEP-API-01 | An anonymous visitor could change their browser label and appear to have a fresh request allowance. | Requests from the same trusted network address share a stable, privately hashed allowance. Changing the browser label no longer resets it. Signed-in limits remain tied to the account. | Rate limits need a stable identifier. Browser-supplied labels are not a security identity. Shared networks can share an anonymous allowance; provider-specific protections still matter. |
| DEEP-DB-01 | The website limited interest requests, but a signed-in caller could bypass that website endpoint and call the database directly. | The database now enforces five new interest requests per hour wherever the request originates. Retrying an existing request does not count twice. A rejected request creates neither a new request nor a notification. | Enforce a business rule where the data changes, so every entry point follows it. Keep the check and write in one transaction. |
| DEEP-API-02 | Two overlapping horoscope uploads could interfere. A failed cleanup could restore an old database pointer after its file had already been removed. | Each upload reserves its own file path. Saving checks that the previous attachment has not changed. Old-file cleanup is recorded separately and retried; cleanup failure never restores stale attachment data. A lost response cannot cause deletion of a possibly successful upload. | Use a conditional update for competing writes. Separate committing new data from retryable cleanup of old resources. |
| DEEP-UI-01 | The deletion dialog looked modal but did not reliably keep keyboard focus inside it or return focus when closed. | It reuses the maintained modal lifecycle: focus enters the dialog, stays inside, Escape cancels when idle, the background is inactive, and closing returns focus. Errors and progress stay inside; short screens can scroll the dialog. | A modal is a keyboard and screen-reader interaction contract, not only a visual overlay. Test opening, errors, cancellation and authentication return. |
| DEEP-UI-02 | “Skip to main content” sometimes pointed to a target that did not exist. | The affected sign-in, account and verification screens now expose a single focusable main-content target, including their alternate states. | Accessibility shortcuts must have working destinations. Test where focus actually moves. |
| DEEP-UI-03 | One accidental photo-delete action permanently removed an upload. | Photo deletion now asks for explicit confirmation. Cancelling, including with a keyboard, sends no deletion request. | Add deliberate confirmation before irreversible user actions. Do not describe a confirmation as an undo mechanism. |
| DEEP-UI-04 | Deletion copy implied access had already stopped and all erasure would finish exactly 24 hours later. | Copy explains that access stops when deletion is confirmed, the next 24 hours are a recovery window, and permanent processing becomes eligible afterward and may take longer. | Describe the actual state machine and operational guarantees. A waiting period is not a completion deadline. |
| DEEP-UI-05 | Private application URLs had inconsistent instructions for search engines. | Protected routes return noindex headers, including exact root URLs, and the access-link shell has matching metadata. Crawlers can read those instructions; sign-in and access checks still protect the content. | Search indexing and authorization solve different problems. Search instructions are never a substitute for access control. |
| DEEP-OPS-01 | Retention cleanup existed as a manual command but was absent from the scheduled maintenance worker, so old counters could remain. | Scheduled maintenance now runs bounded cleanup for each existing retention class independently. Health reports each class's last successful run and overdue count, so a successful identity or email task cannot hide missed retention work. | A cleanup function is incomplete without scheduling, retries, monitoring and proof that the intended records were removed. |

## One reusable interview example

“In VivIntro, we found that two users' actions in different browser tabs could race during an attachment replacement. A cleanup error could undo a successful upload and leave a broken file reference. We changed the save into a conditional database update and recorded file cleanup as durable background work. We then tested overlapping uploads, lost-response behavior and cleanup retries, including against isolated real Storage. The result was that cleanup could fail and retry without corrupting the user's current attachment.”

Keep claims bounded: the local checks demonstrate these scenarios, not perfect security. Historical disclosure references deliberately hold old horoscope objects until their own lifecycle releases them. Production retention success must be confirmed after release; this work does not certify legal compliance or validate every retention class in the wider system.


## Follow-up: clearing every copy of a message

The review found that an interest message was stored in two columns. Cleanup removed one copy and incorrectly reported that it had finished. Cleanup now removes both copies in the same transaction, and monitoring checks the same rule. It also repairs older partially cleared rejected/closed requests and completes both-copy erasure during account deletion. Ordinary retention preserves recent, open and approved requests. The lesson is to test that sensitive data is actually gone from every relevant copy, rather than treating a successful cleanup response as proof.

The correction and latest-main integration are implemented locally. Docker recovery allowed the full clean Supabase replay and all 1,534 database assertions to pass. Production data has not been cleaned by this work.

# VivIntro B2C profile: pilot pressure test and 10-day remediation plan

**Audit date:** 2 October 2026. **Code baseline:** fetched `origin/main` at `b5cfea5` (PR #70); live profile `https://www.vivintro.com/p/<opaque-token>` in the Codex in-app browser. The local checkout is an older, clean `fix/nak-73-mobile-dashboard-summary` branch, so all code pointers below refer to the fetched main revision, not that checkout. Didit startup failure is being handled separately.

## Executive summary

The existing B2C profile is a sound pilot base, not a rebuild candidate: a public projection, authenticated grant projection, 21-character random share token, short-lived signed media, and owner-controlled access are already implemented. However, the mobile gallery viewer has a reproducible touch-exit defect, the 132 px three-row mobile header crowds the profile, and the requested copy/hierarchy is absent. More importantly, the stated pilot rules conflict with current behavior: public links intentionally do **not** expire, and B2C approved access follows the latest approved snapshot rather than pinning the version presented at the request. These need explicit product decisions and server-side regression tests before five-user onboarding. A live owner session and repository inspection do **not** constitute a passed two-account, incognito, database-isolation, or 3G test.

## Security, privacy, SEO, accessibility

- **Token and access:** `nanoid(21)` produces an opaque URL token; rotation and unpublish revoke access. `resolve_approved_portfolio` requires the signed-in grantee, full access, non-revocation and unexpired grant. The B2C model is owner/candidate-scoped rather than a broker tenant. Broker tenant isolation is separate and must be regression-tested, not inferred from this profile view.
- **Consent:** B2C's effective two-sided act is verified viewer request plus owner grant. The database, not merely the button, enforces the grant. Test the exact transitions, grant expiry (15 days per current UI/migrations), rejection/revocation, changed email, second account and stale session. The broker mutual-interest workflow in `20260925120000_mutual_interest_complete_access.sql` is distinct and cannot be used as proof of B2C behavior.
- **Audit:** `record_public_portfolio_view` records at most one portfolio view per hour; grant creation/access/revoke have audit rows. That is insufficient to assert every share/view/contact reveal is captured. Check production migrations and outbox delivery separately. The previously reported `NOTIFICATION_WORKER_SECRET` absence means relationship email notifications should not be considered operational until verified.
- **Metadata:** Live document has a meaningful title/description and H1 = full name, plus section H2s. It has `noindex, nofollow, noarchive`; no JSON-LD was found. No canonical tag was found. A noindex private token page should normally avoid a canonical to a person-identifying URL; make the decision explicit. `src/app/robots.ts` does not disallow `/p/`, so crawlers may fetch links even though the page says noindex. Preview text currently exposes first name.
- **Accessibility:** The photo viewer has dialog semantics, labelled close/next/previous buttons and Escape support, but no evidenced focus trap or restoration. Several decorative images have empty alt text appropriately; informative photos use generic “Portfolio photo,” which should become owner-editable descriptive alt text or a deliberate privacy-safe default. Measure body-text contrast (≥4.5:1) across light/dark themes; not certified in this audit.
- **Performance:** Six-photo live sample is insufficient to certify <3 s on 4G or <6 s on 3G. Measure LCP/CLS/INP on real or throttled devices, especially signed image URLs and initial hero image, before claiming a pass.

## Frame notes for UI implementation

Using the user-supplied Pixel 10 412×924 screenshot as frame A:

1. **Header red-box area:** replace three rows with a 56–64 px single row. Left: logo + “Vivintro”. Right: a 44 px minimum “Show interest” button. Hide Overview/Gallery/Astrology/Details on ≤720 px; desktop can retain section navigation. In an approved or owner view where interest is unavailable, do not show a misleading actionable CTA.
2. **Hero beneath photo:** eyebrow exactly **“A Marriage Introduction”** (title case). H1 remains full name. Next row: `28 years · Arya Vysya` only if each field is public; otherwise omit the missing item. Profession below in muted secondary text: `Data Engineer`, truncate only where needed with an accessible “More” expander. Do not repeat age/community if the quick-facts row remains adjacent.
3. **Gallery overlay:** on 320/375/414 px, dark overlay must cover the header; Close with X and word “Close” at top-right, inside safe area. Outside tap and Escape dismiss; browser Back closes overlay without leaving the profile. On close, return keyboard focus to the photo that opened it.
4. **Mobile bottom CTA:** after hero scrolls away, a safe-area-aware bottom bar says “Show interest”. The top CTA and bottom CTA target the same modal. Hide the bar while a modal/photo viewer is open and for the owner or an approved viewer.
5. **Near share/contact gate:** “Your introduction is private. The owner sees your details only after you submit; direct contact is shared only if they approve.” Near an approved access link: “Available to this signed-in email until [date]. The owner can end access earlier.” If public links remain persistent, never label them expiring.

## Minimal reproducible tests for launch blockers

1. **Lightbox hidden exit:** set viewport 320×720, 375×812 or 414×896; open a clear gallery photo. Expected: visible, tappable Close above all page chrome. Actual on live page: Close y=18–66 sits behind sticky header y=0–132; Escape works. Repeat with keyboard Tab to check trap and return focus.
2. **B2C version drift:** owner publishes version A; viewer requests and owner grants; owner edits a protected field and republishes version B; viewer reloads with same grant. Expected under the stated pilot rule: version A or explicit re-consent. Current database path resolves current `approved_portfolio_snapshots` row B. Run in staging with two accounts and assert actual returned field/media.
3. **Public-link expiry:** publish, record token and expiry; inspect `portfolios.expires_at`/`public_portfolio_snapshots.expires_at`; advance a staging clock or use a short fixture, then GET `/p/<token>`. Expected by requested criterion: expired and unavailable. Current migration sets both expiry fields to `null` on publish; rotation/unpublish are the only normal invalidation.
4. **Consent isolation:** account A requests; before grant, A and unrelated B call approved portfolio/horoscope and Storage. Both must receive no protected data. Owner grants A; A succeeds, B still fails. Revoke/expire A, then A fails again. Verify audit rows without leaking contact data in event metadata.

## QA checklist and pilot acceptance

- Test 320, 375, 414 px plus laptop/desktop; no horizontal overflow, covered controls, inaccessible CTA or form loss.
- Create/publish with Didit liveness; no payment requirement during pilot. Viewer opens token in a **fresh private session**; no URL/query/metadata PII under the chosen policy.
- Viewer request with verified email, owner explicit grant, approved signed-in view, revoke and expiry. A third account and a cross-tenant broker account cannot obtain protected data, media or horoscope via direct API calls.
- Confirm pinned-version behavior matches the Day 1 decision. Check public versus approved gallery counts and photo order; six-photo sample is not enough for stress assurance.
- Confirm share created/copied, public view, request, grant, protected view/contact reveal and revoke have the agreed audit/analytics signals; no raw contact data, OTP, token or signed media URL in event payloads.
- Verify noindex policy, generic OG preview if strict no-PII metadata is adopted, and absence of protected structured data.
- Run repo unit/integration/E2E suite and manual iOS/Android browser tests; record exact device, bandwidth profile and timings.

**Five-user runbook:** invite five pilot creators via admin entitlement; use separate real viewer addresses (not owner's), then walk each through publish, copy link, fresh-browser public view, request, owner decision and approved signed-in viewing. Monitor Didit start/completion, OTP latency/rate limits, notification outbox age, request/grant/audit event counts, 4xx/5xx rates and user-reported navigation friction twice daily. Stop onboarding if protected contact appears without both actions, third-account access succeeds, a modal cannot be exited, or an expired/revoked grant still resolves. Keep a named support contact, rollback deployment and token-rotation procedure ready.

**Recommendation:** iterate on current code. Rebuilding within 10 days would discard working authorization, snapshot projection and audit foundations while increasing privacy risk. Make the three product decisions on Day 1, then use narrow frontend and SQL changes with negative security tests. Do not declare pilot-ready until the unrun live two-account/incognito/mobile-Didit and network tests pass.
